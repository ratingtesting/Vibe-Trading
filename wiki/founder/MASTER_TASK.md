=====================================================
3. TARGET ARCHITECTURE
=====================================================
Principle: CODE = deterministic facts. JEV = selected atomic judgments. CODE = policy composition. RISK = absolute veto. EXECUTION = venue interaction.
Jev is not a strategy, places no orders, sets no risk limits, cannot bypass Risk, cannot flip a strategy candidate's direction (it can only allow, deny or reduce size), and never sees exchange credentials.

Pipeline:
  MarketDataProvider (live) / HistoricalDataProvider (history)
  -> Feature Engine -> Strategy (produces StrategyCandidate, never an order)
  -> State Snapshot (compact, deterministic facts only, no future data)
  -> Jev Judgment (typed atomic questions, one batched call)
  -> Policy Engine (deterministic gates)
  -> Risk Engine (hard veto, can only reduce or deny)
  -> Execution (mode-specific) -> Portfolio -> Journal -> Calibration -> Analytics -> API/SSE -> Web UI

Two separate data planes behind interfaces: HistoricalDataProvider.getCandles(request) and MarketDataProvider (live ticker/book/trades subscription). No venue types (Kuru/Monad/etc.) may appear in domain/core. Existing Kuru/Monad code becomes ONE adapter behind these interfaces.

Modes:
 - BACKTEST: historical data + historical execution simulator.
 - PAPER: live market data + virtual orders + simulated fills from real market data. No real order ever reaches a venue.
 - SHADOW: live market data + real Jev + policy + risk -> record a "would-trade" decision and track its outcome. No virtual order, no paper accounting.
 - LIVE: the only mode allowed to send real orders. Guarded activation (section 9).
Switching modes must not require changing strategy code. The backend keeps running when the browser closes; browser state is never authoritative.

Execution simulators behind one interface (submit/cancel/processMarketEvent -> fills):
 - HistoricalExecutionSimulator: candle-based, signal at bar close executes at the NEXT bar open, with fees, slippage, spread assumptions, order constraints.
 - BookExecutionSimulator: walks the real L2 book for market/IOC-style orders (reproduce the behaviour of A's dry-run once the audit describes it), with fees and latency assumptions.
 - RestingOrderSimulator (limit/post-only): fills only from observed trades or book crossings, with an explicit queue-position assumption. Implement it only if the chosen venue provides a trades feed; otherwise document it as NOT IMPLEMENTED with the reason. If C's paper venue has a post-only lifecycle, audit it and port what is sound.

Event sourcing: every significant event (market, feature, strategy, jev, policy, risk, order, fill, position) is appended to a durable log and can be replayed deterministically.
Decision Record (one object per decision): timestamp, mode, market, instrument, market snapshot, features, strategy id/version, candidate, Jev request, Jev response, Jev resolved model version, Jev latency, policy version, policy gate results, risk gate results, order intent, orders, fills, fees, position, P&L, fallback state.

5. JEV INTEGRATION (use the OFFICIAL contract; do not invent formats)
=====================================================
Read before writing the client: https://docs.typesafe.ai/llms.txt (index), quick start, API reference, Primitives (Choice/Score/Noul), Confidence, Patterns, the JavaScript SDK page, and the agent skill (npx skills add typesafe-ai/skills --skill typesafe-ai).
What the founder's assistant saw in the docs (RE-VERIFY): POST https://api.typesafe.ai/v1/systemone, header Authorization: Bearer $TYPESAFE_API_KEY, body {state, model, questions:{name:{type:"choice"|"score"|"noul", instructions, criteria?}}}; response {model (resolved version like "jev-1.13.0"), answers, usage}; choice -> choice, probabilities, confidence; score -> score, probabilities, confidence, legend; noul -> noul in 0..1 (NO confidence field). All questions in one request are evaluated in parallel: send one batched request per decision.
Rules:
 - "jev-latest" is a moving alias. Record the RESOLVED model string from every response in the Decision Record; allow pinning a specific version by config; a backtest records which one it used.
 - The API key lives server-side only (env), never in the browser, repo, logs or events. Proxy/client uses a fixed destination.
 - Strictly validate every response (types, ranges, probabilities sum, unknown/missing answers). Malformed or late response -> no trade for that decision, recorded as such. Never parse model reasoning text and never fabricate reasoning; show only structured answers and the policy trace generated by code.
 - Retry only the current pending decision. Never substitute a local/mock judgment silently.
 - Questions are atomic and versioned in a config file (id, type, instructions, criteria, version). Initial battery (directional trading; wording is config, refine after reading the docs' guidance on state and instructions):
     regime (choice): trend_up / trend_down / range / breakout / high_volatility / unclear
     alignment (choice): supports_candidate / contradicts_candidate / inconclusive
     setup_quality (score): ordered rubric, e.g. 0 poor .. 3 strong
     adverse_condition (noul): is there a condition in the state that should block this setup?
     persistence (noul): is the setup likely to persist over the planned horizon?
     execution_suitability (noul): are spread/liquidity/volatility acceptable to enter now?
 - State snapshot: compact, computed by code from data available at decision time only. Never ask "should I buy?".
 - Cost control: a config budget cap and a pre-run cost estimate for any backtest that calls Jev. In BACKTEST only, caching by hash(state, question config, resolved model version) is allowed. In PAPER/SHADOW/LIVE no response cache.

=====================================================
6. POLICY, RISK, FALLBACK
=====================================================
Policy (deterministic code, versioned, every gate result logged): ALLOW only if candidate exists AND alignment supports it AND setup_quality >= threshold AND adverse_condition < threshold AND persistence >= threshold AND execution_suitability >= threshold AND confidence (choice/score) >= threshold; otherwise FLAT / NO TRADE. Thresholds live in config, start as placeholders labeled "UNCALIBRATED", and are never delegated to Jev. Separate gates from diagnostics (like B). Policy proposes target direction and size fraction; Risk may only reduce or deny.
Risk Engine (independent, absolute veto): max position notional, max risk per trade, max daily loss, max drawdown, max leverage, max order size, max order frequency, stale market-data timeout, stale Jev timeout, max slippage, min liquidity, kill switch. The kill switch does: cancel all orders + flatten positions + stop trading. Risk limits are code/config, never model output.
Fallback ladder (every step visible in UI and logs):
  healthy + high confidence -> normal
  healthy + low confidence -> reduce size or no trade
  stale or late -> hold, never trade on stale state
  Jev unavailable -> deterministic fallback ONLY if explicitly configured, flagged on every decision
  exchange/account mismatch -> stop new orders
  hard risk breach -> cancel all + flatten + stop
The mock model may exist only as a test fixture or a clearly labeled dev stand-in (visible badge). It must never be used silently in PAPER/SHADOW/LIVE.
Loop discipline (from A): one decision in flight; late -> hold; keep slow work (receipts, fee estimates, analytics) off the hot path.

=====================================================
8. BACKTEST AND CALIBRATION METHODOLOGY
=====================================================
Mandatory: no look-ahead, no future indicator values, correct signal/execution timing (decision at bar close, execution next bar), fees, slippage, spread, realistic sizing and order constraints, chronological train/validation/test split, walk-forward, out-of-sample. Never tune thresholds on the final test period. Do not optimize for maximum historical P&L.
Every run records: market, timeframe, data range and provenance (source, request, checksum), strategy version, parameters, Jev resolved model version, question-config version, policy version, costs, slippage, execution convention, seed.
Compare on identical data and assumptions: A = strategy alone; B = strategy + Jev; C = strategy + Jev + regime filter.
IMPORTANT: historical calls to a current Jev model are NOT out-of-sample evidence (the model may know that period, and aliases change). Label every Jev-assisted backtest with that warning. Real evidence comes only from forward-in-time PAPER/SHADOW logs. B and C are diagnostics until then.
Calibration: persist (state, judgment, policy decision, realized outcome). Define each question's realized outcome deterministically in config (for example: after costs, did the candidate direction beat zero over the horizon). Compute Brier score, log loss, ECE, reliability curve, outcome by confidence bucket, and optional Platt scaling (as in C). Do not assume Jev's native confidence is calibrated for trading; measure it.
